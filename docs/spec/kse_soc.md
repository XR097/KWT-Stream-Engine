# KSE SoC 规格（E203 + 共享 SRAM + KSE 引擎）

> 版本：严格总线门铃方案（v4），2026-11-13；
> 当前实测见第 17 节，第 13/14 节保留 v1/优化轮 2 历史结果。
> 关联 RTL：`rtl/kse_soc/`（`kse_eng_icb.sv`、`kse_accel_sys.sv`、`kse_soc_fifo.sv`、`kse_sys_bus.sv`、`kse_shared_sram.sv`、`kse_sram_ctrl.sv`、生成的 `kse_e203_*.v` / `kse_sirv_plic_top.v`）
> 关联固件：`firmware/kse/`；测试平台：`tb/kse_soc/tb_kse_soc.sv`；脚本：`tools/kse_soc/`
> 依据：`docs/arch/kse-microarch.md` 共享 SRAM 与加载器、E203 职责两节；`docs/spec/kse_top.md`；`docs/spec/kse_shared_sram.md`

## 1. 结构

```text
              E203 (hbirdv2, RV32IMAC, ITCM/DTCM)
               |  BIU
     +---------+-------------------+------------------+
     | mem 总线 O5 0x4000_0000      | PPI O12 0x1100_0000 | PLIC 0x0C00_0000
     v (512 KiB)                    v (4 KiB 有效)        ^ 源 17
  +--------------------------- kse_accel_sys (hfclk / bus_rst_n) -----------+
  |  kse_sys_bus: 一个 sirv_gnrl_icb_arbt（3→1，固定优先级）                 |
  |      m0 = NPU DMA (kse_eng_icb)   m1 = 参数加载器 (SoC 端口, 测试平台)           |
  |      m2 = CPU (E203 O5)                                                  |
  |                              | 单个 32 位 ICB 从口                      |
  |  kse_shared_sram: 1 个控制器 + 32 组 × 2 × RAMSP4096X16 = 512 KiB       |
  |      每拍至多一笔、一拍读、无 bank 并行、无第二个口                       |
  |      总线门铃进度寄存器 -> 引擎（严格 0 滞后放行）                              |
  |  kse_eng_icb: MMIO 寄存器 / 命令队列(2) / 参数段队列(4) / 流式 DMA /       |
  |               4 字流缓冲 x3 / IRQ ---- kse_top (阵列、行存储、预取 FIFO)   |
  +--------------------------------------------------------------------------+
```

严格方案把共享 SRAM 做成 System Bus 上一个普通 32 位 ICB 从设备（地址
`0x4000_0000..0x4007_FFFF`），三个主设备 CPU、参数加载器、NPU DMA 在它前面
由**同一个** ICB 仲裁器合并。v2 的 3×2 交叉开关、两 bank 并行和 DMA 私有口
已删除；NPU 必须以 System Bus 主设备身份经仲裁器访问 SRAM。

- E203 不修改：工程副本由 `tools/kse_soc/make_e203_copies.py` 对固定上游提交
  `5895d5bf` 的文件做精确文本替换生成（每处替换必须恰好命中一次，`--check` 校验仓库内副本是否最新）。
  实例名保持上游命名（`u_e203_subsys_top`、`u_e203_subsys_main`、`u_e203_cpu_top`），上游层次路径可直接使用。

| 上游文件 | 副本 | 改动 |
|---|---|---|
| `perips/sirv_plic_top.v` | `kse_sirv_plic_top.v` | 增加 `io_devices_0_16`（中断源 17），`PLIC_IRQ_NUM` 17→18 |
| `subsys/e203_subsys_plic.v` | `kse_e203_subsys_plic.v` | 增加 `kse_irq` 输入接源 17 |
| `subsys/e203_subsys_mems.v` | `kse_e203_subsys_mems.v` | O5 区域译码为 1 MiB（`O5_BASE_REGION_LSB` 28→20），其中 SRAM 仍为 512 KiB，增加门铃地址，删去示例 AXI 桥与从设备，O5 ICB 导出为共享 SRAM CPU 口 |
| `subsys/e203_subsys_main.v` | `kse_e203_subsys_main.v` | 例化 `kse_accel_sys`；PPI O12（SysPer）接引擎 MMIO，原 `sysper_icb` 端口置空闲；导出加载器端口与 `kse_clk`（=hfclk）、`kse_rst_n`（=bus_rst_n） |
| `subsys/e203_subsys_top.v`、`soc/e203_soc_top.v` | `kse_e203_subsys_top.v`、`kse_e203_soc_top.v` | 透传加载器端口和时钟/复位 |
| `perips/apb_uart/apb_uart.v` | `apb_uart.v`（模块名不变） | 组合块补 `fifo_tx_data = 8'b0` 默认值，消除每个 UART 8 位推断数据锁存器（TX FIFO 只在 `valid_i && ready_o` 时采样数据，闲时值不可观察） |

另有工程自写的 `rtl/kse_soc/kse_tcm_gnrl_ram.v`（模块名 `sirv_gnrl_ram`，替换上游同名 RAM 包装，上游注释标明此处“接 ASIC 存储”）：
ITCM（8192×64）映射为 2×4 个 RAMSP4096X16，DTCM（16384×32）映射为 4×2 个，其它尺寸仍用上游 `sirv_sim_ram`。
时序与 `sirv_sim_ram` 一致（一拍读、字节掩码、不读时保持上次读出值，E203 取指 hold-up 依赖这一点）。这样综合与功耗分析中的 E203 TCM 都是有 Liberty 表征的真实宏。
仿真与综合使用同一份 RTL；上游 `general/sirv_gnrl_ram.v` 与 `perips/apb_uart/apb_uart.v` 不进入文件列表。

所有 SRAM 宏（共享 64 个、TCM 16 个、引擎行存储 32 个与预取 FIFO 8 个）统一用厂商默认 `EMA=3'b010`、`EMAW=2'b00`（见 12 节）。

## 2. 地址映射

| 区域 | 地址 | 说明 |
|---|---|---|
| ITCM | 0x8000_0000，64 KiB | 固件代码（MROM 0x1000 跳转到此） |
| DTCM | 0x9000_0000，64 KiB | 固件数据、bss、栈 |
| 共享 SRAM | 0x4000_0000–0x4007_FFFF | System Bus 上一个 32 位 ICB 从设备；CPU/加载器/NPU DMA 经唯一仲裁器访问 |
| 加载进度门铃 | 0x4008_0000 / 0004 / 0008 | BASE/INIT、WPTR、DONE；经同一仲裁器的一拍 ICB 事务 |
| KSE MMIO | 0x1100_0000–0x1100_0FFF | PPI O12 槽前 4 KiB；O12 其余 16 MiB 地址返回 ICB 错误 |
| PLIC | 0x0C00_0000 | KSE 中断为源 17 |

共享 SRAM 内的任务布局（窗口内偏移，固件 `firmware/kse/kse_soc.h` 与测试平台一致）：

| 偏移 | 字数 | 内容 | 写者 / 读者 |
|---|---:|---|---|
| 0x00000–0x018BF | 1584 | 输入激活（99×64 int8，小端字） | 加载器 / 引擎 DMA |
| 0x018C0–0x4EB3F | 79008 | 参数流 v3（12 层 × 6584 字，层 L 起于 0x018C0 + 26336·L） | 加载器 / 引擎 DMA |
| 0x60000–0x618BF | 1584 | 输出激活 | 引擎 DMA / 测试平台比对 |
| 0x7F000 | 1 | FLAG_START（固件写 1，测试平台据此启动加载器） | E203 |
| 0x7F004 | 1 | FLAG_DONE（通过 0x600D000C；失败 0xBAD0_00xx） | E203 |

加载器一次连续写入输入和参数共 80592 字（镜像 = 输入 + 参数流，一次性格式转换，不计时）。

## 3. KSE MMIO 寄存器（`kse_eng_icb`）

只支持 32 位访问。响应寄存一拍返回，`cmd_ready = !rsp_valid || rsp_ready`。

| 偏移 | 名称 | 属性 | 位定义 |
|---|---|---|---|
| 0x000 | ID | RO | 0x4B534531（"KSE1"） |
| 0x004 | CTRL | RW | [0] 层完成中断使能，[1] 错误中断使能 |
| 0x008 | STATUS | RO | [0] kse_top busy；[1] 有未完成工作；[3:2] 待执行命令数；[4] 队列满；[5] 加载器 done；[6] 写指针有效；[15:8] 完成层数（模 256） |
| 0x00C | IRQ_STATUS | W1C | [0] 层完成，[1] 错误；置位优先于同拍清除 |
| 0x010 | PARAM_ADDR | RW | 下一条命令的参数段字节偏移（[18:2]） |
| 0x014 | PARAM_LEN | RW | 参数段字数 |
| 0x018 | IN_ADDR | RW | 输入（in_en 命令）字节偏移 |
| 0x01C | OUT_ADDR | RW | 输出（out_en 命令）字节偏移 |
| 0x020 | CMD | WO | 写入即入队 {out_en[9], in_en[8], layer[3:0]}，同时锁存当前 PARAM_ADDR/LEN、IN/OUT_ADDR |
| 0x024 | LDR_WPTR | RO | 共享 SRAM 加载器写指针（状态寄存器镜像） |
| 0x028 | LDR_BASE | RO | 加载器本次装载起始地址 |
| 0x02C | DONE_CNT | RO | 复位以来完成的层数 |
| 0x030 | ERR | RO | [0] 队列满时写 CMD；[1] DMA 响应错误（粘滞到复位） |

IRQ = |(IRQ_STATUS & CTRL[1:0])，电平有效接 PLIC 源 17。0x034–0xFFF 和 4 KiB 以外返回 `rsp_err`。

## 4. 命令队列与层完成

- 命令队列 2 项（不含正在执行的命令，后者由 `kse_top` 保存）。每条命令同时把参数段 (PARAM_ADDR, PARAM_LEN) 推入 4 项参数段队列；
  参数 DMA 逐段连续读，下一层参数在本层计算时就流入 `kse_top` 的预取 FIFO（最终配置 PF128，2 KB；`kse_top` 的参数口本来就跨层连续）。
  任意时刻参数段队列至多 3 项占用（2 项待执行 + 已开始执行但尚未开读的 1 项），4 项不会溢出（仿真断言检查）。
- 队首命令在 `kse_top` 空闲（`cmd_ready`）且输出通路已排空时送出；握手时锁存该命令的输入/输出地址与字数（各 1584）。
- **层完成**：`kse_top` 的 `done` 之后，若该层 out_en，还要等最后一笔输出写的 SRAM 响应返回（写缓冲、请求寄存器、在途写全部清空），
  才把 DONE_CNT 加 1、置 IRQ_STATUS[0]。因此固件看到第 12 层完成时，输出已经写入共享 SRAM 宏。

## 5. 流式 DMA（System Bus 主设备，经唯一仲裁器）

- `kse_eng_icb` 的 DMA 是 **System Bus 主设备**：命令/响应经 `kse_sys_bus` 的
  唯一仲裁器进入共享 SRAM 的唯一 32 位从口。v2 的“共享 SRAM 主口 2”私有
  直连已删除。
- 一个 ICB 请求寄存器（地址/数据来自寄存器，满足 ICB“valid 保持到握手”）；
  每拍可装入下一笔，持续 1 字/拍。流优先级：输出写 > 输入读 > 参数读。
- 每个读流有 4 字缓冲；装入读请求时先预留缓冲槽（预留数 + 已存数 < 4），
  响应口恒 `rsp_ready=1`，不会反压 SRAM。在途命令的种类记在 2 项标签 FIFO
  中（总线最多允许 1 笔在途，标签 FIFO 只为扩展性）。
- **放行规则**（`docs/spec/kse_shared_sram.md` 第 8 节），对每个读地址 A：
  `wptr_valid && A >= base && A+4 <= wptr`，21 位比较，不回绕。
  严格方案取 `REL_LAG=0`：只读加载器已经提交的字。`loader_done` 不再放宽
  地址（旧的 4 KB 滞后规则只为 v2 两 bank 相位分离服务）。加载器每 1024 字先收齐全部数据写响应，再经同一 ICB 主口写 WPTR；
  引擎只从片内进度寄存器得到放行信息，TB另按实际数据写握手逐字核验。
- 编译时 `+define+KSE_REL_LAG_4096` 可恢复旧 4 KB 规则，仅用于实测对比；
  交付默认是 0。实测 0 滞后比 4 KB 滞后少 167 拍（见第 15 节）。

## 6. 严格总线仲裁：一个 ICB 仲裁器合并三个主设备

`kse_sys_bus` 例化 E203 上游的 `sirv_gnrl_icb_arbt`（只例化，不改
`third-party/` 源码），`ARBT_NUM=3`、`AW=DW=32`、`ARBT_SCHEME=0`（固定优先
级，端口 0 最高）、`FIFO_OUTS_NUM=1`、`FIFO_CUT_READY=0`、
`ALLOW_0CYCL_RSP=1`。默认端口映射：**0 = NPU DMA，1 = 参数加载器，2 = CPU**。

- **为什么用优先级**：单口下任务总事务数固定（加载器写 80592 + DMA 读
  80592 + 输出写 1584 + CPU FLAG_DONE 1 = 162769），轮询不会增加总带宽。
  引擎参数流一旦断供，QKV/FC1/FC2 等 MM 阶段停摆；DMA 优先让它在每个可读
  字上立即抢到从口，加载器只在 DMA 的请求空档和放行上界处使用剩余周期。
- **加载器为什么不会饿死**：DMA 读流有限、单调、不重复，并受
  `A+4 <= wptr` 约束；DMA 把已提交的字读完后必须停下，加载器随即得到从口。
  加载器每写一个字，最多再产生一个字给 DMA，最坏是 1:1 交替，必然前进。
  契约测试（`tb_sram_prio_contract`）实测加载器最长连续等待 119 拍，尾部
  全部完成；12 任务 SoC 中加载器 80592 字全部写完。
- **CPU 为什么不会死锁**：固件只在窗口前写 FLAG_START、全部层完成且 DMA
  排空后写 FLAG_DONE；窗口内只访问引擎 MMIO（PPI O12）和 PLIC，不访问
  共享 SRAM。因此 CPU 最低优先级不影响功能，也不存在“CPU 等待 SRAM 才能
  让 DMA 前进”的环。
- **为什么没有轮询实现**：上游 `sirv_gnrl_icb_arbt` 的 `ARBT_SCHEME=1`
  会例化 `sirv_gnrl_rrobin`，而本仓库固定的 E203 上游快照（`5895d5bf`）
  没有这个叶子模块；本任务不改 `third-party/`，所以采用上游的固定优先级
  模式，没有自写仲裁器。
- **响应与吞吐**：`rspid` 单表项使整个总线最多一笔未完成事务；从口一拍
  返回，响应被消费的同一拍可接收下一笔命令，因此持续吞吐仍是 1 字/拍。
  实测 12 任务每任务从口事务恰好 162769 笔，端口利用率 99.85%。

实测对比（12 任务 SoC，同一固件/golden，均逐字节通过）：

| 变体 | 窗口周期 | tasks/s | 加载器跨度 / 等待 | 参数饥饿拍 |
|---|---:|---:|---:|---:|
| **DMA > loader > CPU，REL_LAG=0（采用）** | **163015** | **920.16** | 161182 / 80590 | 40064 |
| DMA > loader > CPU，REL_LAG=4096 | 163182 | 919.22 | 160159 / 79567 | 40626 |
| loader > DMA > CPU，REL_LAG=0 | 180358 | 831.68 | 80592 / 0 | 83781 |

## 7. 固件（`firmware/kse/`）

- 工具链：xPack `riscv-none-elf-gcc` 15.2.0-1，`-march=rv32imac_zicsr -mabi=ilp32 -O2`。
  `make -C firmware/kse BUILD=<dir>` 生成 ELF、反汇编和 ITCM 镜像（`tools/kse_soc/bin2itcm.py`，每行一个 64 位字）。
- 启动：栈和数据在 DTCM，`mtvec` 直接模式，陷阱入口保存调用者保存寄存器后调用 `trap_handler`。
- 流程：配置 PLIC（源 17 优先级 1、使能、阈值 0）、检查 ID、CTRL=3、IN/OUT_ADDR、PARAM_LEN=6584，打开 MEIE；
  写 FLAG_START；下发第 0、1 层；之后循环 `关 MIE → 检查完成 → WFI → 开 MIE`（避免检查与 WFI 之间丢失唤醒）。
- 中断处理：mcause 必须是机器外部中断，否则写失败标志停机；claim → 读 IRQ_STATUS 并写回清除 → 读 DONE_CNT，
  每多完成一层就下发下一层（第 L 层完成时下发 L+2，始终保持 L+1 在队列中）→ complete。
- 12 层完成后检查 ERR=0、STATUS 无未完成工作、DONE_CNT=12，写 FLAG_DONE=0x600D000C（任何错误写 0xBAD0_00xx）。

## 8. 计时口径（官方答疑 2）

- 窗口起点：加载器第一笔写命令握手（`kse_ldr_cmd_valid && kse_ldr_cmd_ready` 的采样沿）。
- 窗口终点：E203 对 FLAG_DONE 的写命令在共享 SRAM CPU 口握手的采样沿。
- 窗口周期 = 两沿在 hfclk 计数器上的差值。复位、ITCM 装载、读文件、镜像生成（格式转换）不计。
- 窗口内包含：输入与全部参数的实际传输（每拍至多一字，真实 SRAM 端口时序与仲裁）、DMA 等待放行、E203 下发命令、中断与调度、
  引擎计算、输出写回共享 SRAM。
- 任务之间整机复位；共享 SRAM 全部 64 个宏清零，引擎行存储和预取 FIFO 宏置 X，DTCM 清零，重新装载 ITCM（均不计时）。

## 9. 活动统计接口

`tb_kse_soc` 的 `+ACT=saif|fsdb +ACT_TASK=<k> +ACT_FILE=<文件>` 在第 k 个任务的窗口内打开整个 `u_soc` 的翻转统计：
SAIF 用 `$set_toggle_region/$toggle_start/$toggle_stop/$toggle_report`（v2 历史：task 0 的 SAIF DURATION 414252 ns = 103563 拍 × 4 ns；严格方案本轮未重新生成活动文件）；
`+ACT_TASK=-1` 在所有任务的窗口内累计（窗口之间暂停计数），仿真结束时写一个 SAIF，DURATION 为各窗口之和。
`+CLK_HALF_NS=3.3335` 让 hfextclk 周期为 6.667 ns（lfextclk 保持 16.5 倍，即 110 ns），SAIF 时间即真实 150 MHz 时间；
v2 功耗分析用的 12 窗口 SAIF DURATION 为 8285454.25 ns = 1242756 拍 × 6.667 ns；严格方案 12 窗口为 1956180 拍，若按 6.667 ns 口径应为 13041852.1 ns，供后续功耗轮次使用。
FSDB 需编译时加 `+define+KSE_FSDB` 并链接 Verdi PLI。窗口起止比计时沿各晚一拍（开关在标志置位的下一拍执行）。

## 10. 验证

`tools/kse_soc/kse_soc_sim.sh`：`fw`、`data`、`build`、`run`、`regress <名字> [并行数]`。
测试平台判据见 `tb_kse_soc.sv` 文件头：FLAG_DONE 为通过码；输出 6336 字节逐字节等于 `sample_XX_output`（比较字节数必须等于 6336）；
DMA 恰好写 1584 个输出字且各一次；DMA 恰好读 80592 个镜像字各一次且读回值等于加载器写入值；每笔 DMA 读按共享 SRAM 寄存的
写指针和严格放行规则（`A>=base && A+4<=wptr`，`REL_LAG=0`）复核；加载器写 80592 字并 done；12 条命令（层号、in_en/out_en 正确）、
12 次 kse_top done、12 次层完成；无超时；日志中任何 `ERROR`/`Error`/`Fatal`/`MISMATCH`/`TIMEOUT` 都判失败。

严格方案新增逐拍断言（TB 计数器 + RTL `ifndef SYNTHESIS` 断言）：主设备握手数 ≤1；SRAM 从口握手恰好等于某一个主设备握手；
SRAM 宏组选择 `$countones(grp_sel) <= 1`（每拍至多一个 32 位字/一对低高宏被访问）；从口在上一响应未消费时不得接收新命令。

## 12. 已知限制

### 12.1 严格方案

- **单口串行化是主要代价**：加载器写 80592 字和 NPU DMA 读 80592 字必须
  分时占用同一个 32 位口。12 任务窗口 163015 拍（v2 100794 拍，+61.7%），
  150 MHz 下 920.16 tasks/s（v2 1488.18，−38.2%）。单口事务下限 162769 笔，
  实测只比理论下限（含 154 拍 E203 收尾）高 92 拍（0.056%），端口利用率
  99.85%；再优化仲裁/预取的空间很小，除非改变“一个 32 位从口”的合规前提。
- **引擎 MM 阶段被拉长**：参数供应平均约 0.5 字/拍，QKV/FC1/FC2 等参数密集
  阶段约 2 倍（如第 1 层 QKV 1274→2686、FC1 1568→2397、FC2 1911→4785），
  SC/SM/PV/PJ/LN 等非参数阶段不变。参数饥饿拍 40064（v2 4215）。
- **固定优先级在契约外会饿死低优先级主口**：三个主口持续请求同一地址的
  对抗性流量会把加载器饿死；这不是 KSE DMA 契约（有限、单调、受水位约束）
  内的场景。契约测试和 12 任务 SoC 已验证加载器前进。
- **没有轮询模式**：上游固定快照缺少 `sirv_gnrl_rrobin` 叶子模块，本任务
  不改 `third-party/`，故只用上游固定优先级。
- **面积/功耗未重测**：本任务不做 DC/功耗，严格方案的门数、setup/hold 和
  功耗需后续轮次；v2 的 1.410501 mm² / 163.329205 mW 不能直接沿用。
- **4 KB 相位滞后不再需要**：严格方案用 `REL_LAG=0`，只读已提交字；实测比
  保留 4 KB 滞后少 167 拍（0.10%），并去掉启动阶段输入流被滞后 4 KB 的延迟
  （输入饥饿 1538 拍 vs 2560 拍）。

### 12.2 v2 历史限制

- 第 0 层比单独引擎多 1569 拍（实测：IN 阶段 +979，QKV 阶段 +531，其余阶段与第 1 层相同）。输入与 QKV 参数（共 3176 字）都要经过同一条
  1 字/拍的加载器→共享 SRAM→DMA 通路，且放行规则要求加载器领先 4 KB（1024 拍）。把参数排到输入前只是把延迟从 QKV 移到 IN：
  每提前 1 个参数字，输入就晚 1 拍。按“QKV 最后一个参数字的流位置 3176 + 1024 拍滞后”估计，下限约为比单独引擎多 1340 拍，
  不能在现有规则下消除（单独引擎有独立的参数口和激活口，开头每拍可收 2 字）。
- SRAM 宏 `EMA`：Liberty（`RAMSP4096X16_tt_1p10v_1p10v_25c.lib`、`RAMSP1024X16_tt_1p10v_1p10v_25c.lib`）对 EMA 全部 8 种取值都有 CLK→Q 表与按 EMA/EMAW 区分的
  CLK 内部功耗。tt 1.10 V 25°C 下 CLK→Q：RAMSP4096X16 EMA=000 为 1.19–1.57 ns，EMA=010 为 1.42–1.80 ns；RAMSP1024X16 EMA=010 为 0.99–1.37 ns；
  注释给出的最小周期 2.845 ns / 1.930 ns，均远小于 6.667 ns。因此统一改用厂商默认 EMA=3'b010（共享 SRAM 原为 000）。

## 15. 严格总线方案（2026-11-12）

### 15.1 结构

- 共享 SRAM：System Bus 上**一个** 32 位 ICB 从设备，地址
  `0x4000_0000..0x4007_FFFF`，64 个 `RAMSP4096X16` 组成 32 组 × 2 宏的
  128K×32 平坦阵列；每拍至多一笔、一拍读、没有 bank 并行和第二个口。
- 仲裁：SRAM 从设备前**一个**上游 `sirv_gnrl_icb_arbt`（`kse_sys_bus`），
  合并 CPU O5、参数加载器、NPU DMA 三个主设备；默认固定优先级
  DMA > loader > CPU。
- NPU：DMA 是 System Bus 主设备，经同一仲裁器访问 SRAM；控制寄存器仍走
  PPI O12 MMIO，中断仍是 PLIC 源 17，加载器写指针放行规则保留（严格 0 滞后）。
- 加载器：仍是测试平台 ICB 主设备，写入经同一仲裁器进入 System Bus，不直连 SRAM。
- E203 上游源码不改；工程副本由 `make_e203_copies.py` 生成，`--check` 通过。

### 15.2 理论下限

单口 SRAM 每笔事务占一拍；任务内必然发生的事务：

| 来源 | 笔数 |
|---|---:|
| 加载器写输入+参数镜像 | 80592 |
| NPU DMA 读输入+参数镜像 | 80592 |
| NPU DMA 写输出 | 1584 |
| CPU 在窗口内写 FLAG_DONE | 1 |
| **合计** | **162769** |

窗口起点是加载器第一笔写握手（FLAG_START 写在其前，不计入窗口）；窗口终点是
CPU 写 FLAG_DONE 的握手，因此窗口内 CPU 只有 1 笔。单口容量给出的下界是
162769 − 1 = 162768 拍（N 笔占 N 个采样沿）。若再假定收尾固定为当前固件实测的
154 拍（最后层完成事件 → FLAG_DONE 握手），并计入末写到层完成事件至少 2 拍，
则条件性下界为 (162768 − 1) + 2 + 154 = 162923 拍；这不是与固件无关的普适下限。实测 163015 拍，只高 92 拍（0.056%）；从口忙碌 162769 拍，
利用率 99.85%（162769/163016）。

| LN2（phase 10） | 1 | 1 | 0 |

结论：参数供应从 v2 的约 0.81 字/拍降到约 0.5 字/拍，MM 阶段约 2 倍；
非 MM 阶段不变。总窗口由单口事务数下限决定，引擎饥饿的周期与加载器占用从口
的周期重叠，因此没有额外超出下限。

### 15.5 变体实测

| 变体 | 窗口周期 | tasks/s | 相对默认 | 说明 |
|---|---:|---:|---:|---|
| **DMA > loader > CPU，REL_LAG=0（采用）** | **163015** | **920.16** | — | 只读已提交字，启动快 |

### 15.6 遗留问题

- 严格方案的单口串行化使吞吐比 v2 低 38.2%，这是合规的固有代价；除非改变
  “共享 SRAM 是 System Bus 上单个普通从设备”的前提，否则无法回到 v2 水平。
- 本任务不做 DC 综合和功耗；严格方案面积、时序、功耗需后续轮次重新测量。
- 轮询模式未实现（上游快照缺 `sirv_gnrl_rrobin`）；固定优先级在契约外会
  饿死低优先级主口，交付场景（KSE DMA 契约）已验证不会。

## 16. 严格方案 PPA 优化默认配置（2026-11-13）

162992拍/任务、920.29tasks/s，计分面积1.238717mm²，整SoC功耗127.512464mW，
平均每任务能耗138.563672µJ，相对本轮严格基线Δscore=+2.115769。

## 17. 最终门铃方案（2026-11-13，优先于历史性能数据）

按 Q16/Q17，加载器仅保留 32 位 ICB 口，删除所有 wptr_init/value/we/wdata/done
旁路输入。进度寄存器位于仲裁器后，在 SRAM 512 KiB 之外、平台 0x4000_0000
区域内；BASE/INIT、WPTR、DONE 的协议详见共享 SRAM spec 3.3。
CPU/固件 FLAG_START、FLAG_DONE、MMIO O12、PLIC17 和引擎数值均不变。
窗口从第一笔门铃写开始，至 FLAG_DONE 写握手，包含全部门铃开销。

首任务 256 字粒度：317 笔门铃、164338 拍；1024 字粒度：81 笔门铃、163328 拍，
采用后者。总事务下限 162769+ceil(80592/1024)+2=162850，包含 BASE、最终
WPTR、DONE（最终 WPTR 已计入 ceil）。12任务实测和最终PPA见 `docs/history.md` 的 strict-final 一节，不沿用旧周期或旧 SAIF。

`make_e203_copies.py --check` 同时检查 SoC 加载器端口集合恰为 ICB 的十个信号；
TB对每个 DMA 读额外检查对应数据已真实握手写入，门铃超前会报 ERROR 并使测试失败。
